# Proposal: 消防设施报警处置端点（按报警 id 复用故障处置能力）

## 背景

消防设施报警（`GET /fire-facility/alarms`）是故障工单 `fac_fire_facility_fault` 的**派生命名视图**
（`id=AL-<故障号数字部分>`），此前只有读端点、无写端点：要处置一条报警，必须跳转到「消防故障」台账
人工定位对应故障工单，才能推进状态。管理端报警列表自身没有任何处置入口，值班员无法在报警视图内闭环
「确认 / 派单 / 维修 / 验收 / 闭环」。

## 目标

- 新增 `PUT /api/v1/fire-facility/alarms/{alarmId}`：按报警 id 反查底层故障，复用既有故障处置能力
  （确认/派单/维修/验收状态流转 + 派单/维修/验收字段局部更新 + 故障时间线追加）。
- 权限**复用** `fire-facility:handle`（V68 已登记并授权 ADMIN 及五类岗位角色），不新增权限码。
- 复用 `updateFault` 自带的 `@RealtimeSync(domain="fire-facility.fault")` 广播；报警视图已订阅该域，
  处置后报警列表自动重拉刷新，无需新增广播域。

## 非目标

- 不为报警新建实体表 / 独立状态机：报警始终是故障的派生视图，「处置报警」=「处置底层故障」。
- 不改 `GET /fire-facility/alarms` 的响应 schema（仅修正契约示例里 `id` 的整数漂移）。
- 不改故障状态枚举（`待确认→已确认→已派单→维修中→待验收→已闭环`）与级别枚举。

## 分级

**L3** —— 仅新增业务写端点，复用既有表 `fac_facility_fault` / `fac_fire_facility_fault_timeline`，
不触及鉴权/令牌/过滤器、权限模型、数据库结构、密钥策略，无需人工确认关卡即可实施。
处理动作范围与交互形式已与需求方确认（完整流程 + 弹「处理」对话框）。
