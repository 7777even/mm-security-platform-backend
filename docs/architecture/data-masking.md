# 数据脱敏设计（Data Masking）

> 敏感字段在**日志**与**响应出口**的脱敏设计真源。当前为**待落地设计**，本文作为实现约束；改动脱敏策略属 **L3**（业务能力），须 proposal + 评审。本文与 `password-security.md`、`audit-log.md` 配合。

## 1. 决策（Decisions）

- **脱敏只在「出口」做**：日志 MDC 与 API 响应序列化阶段脱敏；**数据库中存储字段不脱敏**（否则无法精确匹配 / 检索）。即「存真、出掩」。
- **集中策略，禁止散落**：引入 `common/MaskUtil`（或等价组件），按字段类型登记脱敏策略（手机号 `138****8000`、身份证 `110***********1234`、设备编码 `MDM-****`、姓名 `张*`）。各业务代码**调用**策略，不得各自手写正则。
- **日志脱敏**：`TraceContext` / 日志切面在输出前对 MDC 中的 `username`、`deviceCode` 等敏感键脱敏；业务代码 `log.info("user={}", user.getUsername())` 不再需要手动处理。
- **响应脱敏**：通过 Jackson `@JsonSerialize(using=MaskingSerializer.class)` 或 DTO 映射阶段调用 `MaskUtil`，确保 `realName`、`phone` 等字段在 `Result<T>` 序列化时被掩。
- **审计先行**：`audit-log.md` 要求写入 `fac_audit_log.detail_json` 前先脱敏——审计表是敏感汇聚点，优先覆盖。

## 2. 现状（Current State）

| 项 | 状态 |
| -- | ---- |
| `common/MaskUtil` / `MaskingSerializer` | ⚠️ **未实现**（设计待落地） |
| 日志 MDC 自动脱敏 | ⚠️ 未实现 |
| 响应级 `@JsonSerialize` 脱敏注解 | ⚠️ 未实现，当前靠 DTO 手工排除（如 `AuthService.me()` 只选 3 字段） |
| `passwordHash` 不出现于响应 | ✅ 靠 DTO 映射保证（非系统级脱敏） |

> 现状下脱敏是「点状」的（靠开发者自觉选字段），无统一策略层，存在遗漏风险——本文旨在把点状升级为集中策略。

## 3. 约束（Constraints）

- **永不**对数据库存储列做脱敏（影响等值查询、关联、唯一约束）。
- 脱敏策略为**白名单**：仅登记的类型被掩，未知字段默认原样（避免误掩业务含义字段）。
- 管理后台 / 运维接口如需看明文，须独立权限层（RBAC `ADMIN` + 独立端点），不在通用列表接口放开。
- 脱敏不涉及聚合统计字段（如报警计数），仅针对可识别个人 / 设备的直接标识符。

## 4. 反模式（Anti-patterns）

- ❌ 在数据库里存脱敏值 —— 破坏检索与一致性。
- ❌ 业务代码各自写 `replaceAll` 正则 —— 策略漂移、漏改即泄露。
- ❌ 把 `passwordHash`、身份证号误放进 `Result` 详情 —— 即使哈希也属敏感，须排除或掩。
- ❌ 把脱敏做成「永远掩」的全局拦截器 —— 管理明文需求无法满足，应留受控出口。
